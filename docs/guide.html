·開始之前

前端一樣是純靜態網頁（放 GitHub Pages），差別是後端從「Google Apps Script + 試算表」換成「Firebase Authentication + Firestore」，而且前端直接讀寫資料庫（沒有中間的 API 伺服器），權限與資料驗證全部寫在 Firestore 安全規則（firestore.rules）裡。你只需要準備：

一個 Google 帳號（拿來開 Firebase 專案，完全免費的 Spark 方案，不用綁信用卡）
一個 GitHub 帳號（放前端靜態網頁，用 GitHub Pages 發佈，跟一代一樣）
約 15 分鐘不被打斷的時間
✅ 跟一代比，變快 / 變簡單的地方
  • Firestore 讀寫比 Google 試算表快很多，投票即時反映不用等 10 秒輪詢
  • 不用再手動驗證 Google ID token（tokeninfo API），Firebase Authentication 直接處理，也不用發布「正式版」OAuth 應用程式那一步
  • 沒有 Apps Script 每日執行時數 90 分鐘的隱形上限問題

A建立 Firebase 專案

  1. 前往 console.firebase.google.com →「新增專案」，專案名稱隨意（例如 jioka2）
  2. 是否啟用 Google Analytics：不需要，關掉即可
  3. 建立完成後，左上角齒輪 →「專案設定」→ 頁面最下方「你的應用程式」→ 點網頁圖示 </> 新增一個網頁應用程式（不用勾 Firebase Hosting）
  4. 複製顯示出來的 firebaseConfig 物件（apiKey / authDomain / projectId...），步驟 D 要用

B啟用 Authentication（Google 登入）

  1. 左側選單「Authentication」→「開始使用」→「Sign-in method」分頁
  2. 啟用「Google」提供者，填一個對外顯示名稱 → 儲存
  3. 展開該提供者的「網路用戶端 ID」/「Web SDK 設定」，複製那組 xxxxx.apps.googleusercontent.com —— 這就是步驟 D 要填的 GOOGLE_CLIENT_ID
  4. Authentication →「Settings」→「已授權網域」：確認之後要用的 GitHub Pages 網域（<你的帳號>.github.io）有在清單裡，沒有就手動加入
不需要像一代那樣額外去 Google Cloud Console 申請 OAuth 用戶端、也不需要「發布正式版」——Firebase 幫你處理好了，任何 Google 帳號都能直接登入。

C建立 Firestore 資料庫 + 部署安全規則

  1. 左側選單「Firestore Database」→「建立資料庫」→ 選一個離使用者近的地區（例如 asia-east1）→ 用「正式版模式（production）」啟動（規則之後會整份覆蓋掉，選哪個起始模式都沒差）
  2. 把本專案 firestore.rules 整份內容複製，貼到 Firestore Database →「規則」分頁，覆蓋掉預設內容 → 發布
  3. （可選，若你熟 CLI）也可以用 Firebase CLI 部署： 
    npm i -g firebase-tools
firebase login
firebase use --add   # 選這個專案
firebase deploy --only firestore:rules
這份規則是整個服務唯一的權限與資料驗證層（沒有後端伺服器把關），務必整份貼上、不要只挑幾行改，也不要在主控台的規則編輯器裡手動加東西。

D設定前端 docs/config.js

把步驟 A 的 firebaseConfig 和步驟 B 的 Client ID 填進去：

window.JIOKA_CONFIG = {
  firebase: {
    apiKey: '...',
    authDomain: 'your-project.firebaseapp.com',
    projectId: 'your-project',
    storageBucket: 'your-project.appspot.com',
    messagingSenderId: '...',
    appId: '...',
  },
  GOOGLE_CLIENT_ID: 'xxxxx.apps.googleusercontent.com',
};

E部署到 GitHub Pages

  1. 把整個 jioka2 專案推到一個新的 GitHub repo（跟一代的 jioka repo 分開，互不影響）
  2. repo 頁面 →「Settings」→「Pages」：Source 選「Deploy from a branch」，Branch 選 main，資料夾選「/docs」→ Save
  3. 等 1～2 分鐘，開啟 https://<你的帳號>.github.io/jioka2/
實際網域要跟步驟 B 的「已授權網域」一致，不然登入會失敗。

·三種身分怎麼用

跟一代完全一樣的玩法：誰先對某場活動建立/投票，誰就是主揪。

👑 主揪（發起人）
  1. 首頁「🎉 發起揪咖」→ 登入 → 填名稱、類型、說明、截止時間
  2. 月曆點日期 → 勾時段（可複選/自訂）；填地點名稱 + Map 連結，可加多個
  3. 送出後把連結丟 LINE 群組（Modal 內建 LINE 分享）
  4. 管理後台可以：看明細、刪留言/選項、延長或提前結束投票、指定次管理者、標記最終方案、下載 CSV
🙋 參與者
  1. 打開連結 → Google 登入 → 設定本場暱稱（同場不能撞名）
  2. 點候選日期勾時段；點還不是候選的日期可「提議新日期」
  3. 地點點「我可以」（可複選），也能「新增候選地點」；截止前隨時可改
🤝 次管理者
  • 由主揪在後台輸入 Gmail 指定；對方就算還沒登入過也能先加，等他第一次用該帳號打開活動時自動生效
  • 能新增候選日期/地點、刪除留言、查看投票明細；不能改主揪已建立的選項與活動設定

·資料放在哪些 Firestore 集合

每場活動是 events/{eventId} 一份文件，底下掛子集合。Email 一律只放在 private/roles 與 participantsPrivate 這兩個私有子集合，一般訪客與其他參與者看不到。

路徑存什麼備註
events/{id}活動主檔（公開欄位）：標題、類型、截止時間、最終方案、ownerUidopen / closed / confirmed / deleted（軟刪除）
events/{id}/private/roles主揪/次管理者 Email 名單只有主揪/次管理者讀得到
events/{id}/options/{oid}候選日期＋時段 或 候選地點＋Map 連結isDeleted 軟刪除
events/{id}/votes/{uid}某人在這場活動投的所有選項doc id = uid，改票直接覆寫整份，不用鎖
events/{id}/comments/{cid}留言，可指向特定選項僅 管理者 可刪（軟刪除）
events/{id}/participants/{uid}暱稱、加入/最後訪問時間公開，暱稱同場唯一
events/{id}/participantsPrivate/{uid}Email只有本人與管理者讀得到
events/{id}/nicknames/{nickname}暱稱佔用登記doc id 本身天生唯一，達成搶佔式唯一性
userJoinedEvents/{uid}/items/{eid}「我參加過的活動」索引只有本人讀得到
併發保護
投票用 doc id = uid 直接覆寫整份，天然不需要全域鎖，不會像一代那樣人多時卡住
即時性
前端用 Firestore onSnapshot 訂閱，資料一變就推送，不用輪詢等待
免費額度
Spark 方案每天 5 萬次讀取 / 2 萬次寫入，一般朋友揪團規模用不完

?常見問題

登入按鈕沒出現，或登入失敗？

檢查 Firebase Authentication →「Settings」→「已授權網域」是否包含你實際開啟的網域。config.js 裡的 GOOGLE_CLIENT_ID 要跟 Authentication → Sign-in method → Google 那組一致。

跟舊版 jioka（試算表版）資料會混在一起嗎？

不會。這是完全獨立的 Firebase 專案、獨立的 GitHub repo，兩邊資料庫互不相通，舊版連結一樣可以繼續用。

改了 firestore.rules 之後前端行為沒變？

規則要重新「發布」（主控台的規則分頁）或重新 firebase deploy --only firestore:rules 才會生效，不是存檔就自動套用。

資料會不會遺失？誰看得到？

所有資料存在你的 Firebase 專案 Firestore 裡，權限完全由 firestore.rules 把關（沒有後端伺服器）。刪除活動/選項/留言都是軟刪除，要復原可以在 Firebase Console 手動改欄位。

🔒隱私與安全

  • 登入採 Firebase Authentication + Google 提供者，只取 Email 與顯示名稱，不存密碼；Google ID token 由 Firebase 後端驗證，前端不用自己驗
  • 公開可讀的活動資料（給任何持有連結的人看）完全不含任何人的 Email，只有暱稱
  • Email 只存在 private/roles（管理者名單）與 participantsPrivate（每人的 Email），只有主揪/次管理者、以及本人自己讀得到
  • 沒有後端伺服器，所有資料存取規則寫在 firestore.rules，是整個系統唯一的安全邊界，改動請小心測試
